AI-Assisted Quality Engineering: What Actually Works

Not another "AI will replace testers" post. This is a field report from actually using ChatGPT, Claude, Copilot, Cursor, and Gemini inside a real QA workflow — what saved time, what produced garbage, and where I still don't trust it.

Nigar Kana · 11 min read · AI · Quality Engineering
AI-Assisted Testing LLMs Playwright Prompt Engineering

Most "AI in QA" content falls into one of two camps: breathless claims that testers will be obsolete in two years, or a listicle of prompt templates nobody actually ran against a real project. I wanted to write neither. This is what happened when I ran AI tools against actual tasks from my own testing work — generating test cases, writing Playwright scripts, building synthetic data, and triaging failures — and where I hit a wall each tool couldn't get past.

Generating test cases from Jira-style user stories

Feeding a user story into an LLM and asking for test cases is the most common AI-QA demo, and it's a genuinely good starting point — with a large caveat. Given a story like "As a permitting officer, I can reject a submitted permit with a reason code," ChatGPT and Claude both reliably produce the obvious cases: happy path rejection, rejection without a reason code, rejection of an already-approved permit. What they don't produce without explicit prompting is the case that actually matters on a government system: what happens to the audit trail when a rejection is later reversed, or whether a rejected applicant can resubmit under the same permit ID. That's domain knowledge, not something inferable from the story text alone. The workflow that works: use the model to generate the first 70% of obvious coverage fast, then spend my own time on the 30% that requires knowing the system's actual risk profile — the part no story text captures.

Generating Playwright scripts from natural language

This is where the productivity gain is most real. Describing a flow in plain language — "log in, add two products to the cart, remove one, verify the remaining item's price" — and getting back a rough Playwright script saves real scaffolding time, especially with Copilot and Cursor operating directly inside the editor with access to my existing page objects. The catch: generated scripts default to brittle selectors (text matching, nth-child) unless the model can see my Page Object Model conventions already in the file. Cursor and Copilot, working with open-file context, do noticeably better here than a copy-pasted ChatGPT response with no visibility into my actual codebase — they'll reuse an existing `loginPage.login()` method instead of reinventing raw locator chains. The lesson: AI-generated test code is only as good as the context window it can see. Bare prompts in a chat window produce generic code; tools wired into your actual repo produce code that fits your architecture.

Producing synthetic test data

This is close to a solved problem and one of the highest-value uses I've found. Asking for 50 synthetic user records with realistic edge cases — names with apostrophes, addresses with unit numbers, emails with plus-addressing, phone numbers in multiple formats — takes seconds and reliably surfaces validation bugs that hand-typed test data ("John Smith", "test@test.com") never would. On a fintech-style module involving loan repayment scheduling, generating synthetic edge-case amounts (partial payments, values one cent off a rounding boundary, negative adjustments) found more genuine data-handling bugs than the manually authored test data set did. The one thing to watch: never generate synthetic data that resembles real customer PII patterns closely enough that it gets confused for real data in logs or screenshots later.

Explaining failing tests and root-cause analysis

Pasting a Playwright failure trace — the assertion, the stack, the relevant DOM snapshot — into Claude or ChatGPT and asking "why did this fail" is now a normal part of my triage process, not a novelty. It's genuinely fast at distinguishing "this is a selector that no longer matches because the DOM changed" from "this is a timing issue, add a wait condition" from "this assertion is actually correct and the application regressed." What it can't do reliably is root-cause analysis that requires knowledge outside the trace itself — it doesn't know that a specific flaky test always fails on Mondays because of a scheduled data refresh, or that a similar-looking failure happened in a different module three releases ago for an unrelated reason. AI is good at reading logs. It has no memory of your system's history unless you feed it that history explicitly, every time.

Defect summarization

This might be the single most underrated use case. Turning a wall of raw defect data — ticket IDs, severities, one-line descriptions — into a two-paragraph summary for a stakeholder who doesn't want to read 40 tickets is exactly the kind of compression work an LLM does well and a human does slowly. I use this before sprint reviews: paste the sprint's defect list, ask for a summary grouped by module and severity, with the pattern called out ("6 of 9 new defects this sprint touch the checkout flow"). It reliably surfaces patterns a flat list hides. It does not replace judgment about which defects actually matter — a model will happily summarize "9 defects found" without knowing that one of them is cosmetic and another blocks checkout entirely, unless the severity data is accurate and I ask it to weight accordingly.

Visual regression using AI

This is the least mature area of the ones I've tried, and I want to be honest about that rather than oversell it. AI-assisted visual diffing tools promise to distinguish "meaningful layout regression" from "anti-aliasing noise" automatically, and in my experimentation the signal-to-noise ratio is still rough — they flag font-rendering differences between CI runners as confidently as they flag an actually broken layout. It's a space worth watching, not a space I'd currently trust as a release gate without a human reviewing every flagged diff. Traditional pixel-diffing with a sane threshold, reviewed by a person, still outperforms what I've tested from AI-driven visual regression in terms of actual trust.

Where AI still fails

  • Judging what actually matters. It generates coverage evenly across a spec regardless of business risk. It doesn't know that the billing module deserves 3x the scrutiny of the "About Us" page unless you tell it, every time.
  • Institutional memory. It doesn't know your team's history of flaky tests, past incidents, or why a particular workaround exists in the codebase — context that lives in people's heads, not in the code it can see.
  • Confident wrongness. A generated test case or a root-cause explanation can be fluent and entirely wrong, and it reads exactly as confidently as a correct one. Every output needs a human who understands the system checking it — treating AI output as a draft, not an answer.
  • Genuinely novel exploratory testing. The kind of testing where you're poking at a system with no script in mind, following a hunch about where a boundary might be soft — that instinct doesn't come from pattern-matching against training data, it comes from having broken enough systems to have intuition about where they break.

Quick notes on the tools, from actual use

  • ChatGPT — best general-purpose reasoning for triage and summarization; no native visibility into my codebase unless I paste context in manually.
  • Claude — strong at longer, more careful reasoning through multi-step root-cause questions and at holding a large amount of pasted context (logs, multiple files) without losing the thread.
  • GitHub Copilot — the tightest in-editor loop for scaffolding test code, because it sees my actual page objects and file structure as it suggests completions.
  • Cursor — similar strength to Copilot but with more control over exactly what context it's given, which matters when a repo has conventions a plain autocomplete would ignore.
  • Gemini — useful as a second opinion when cross-checking a generated explanation or test case against a different model's read of the same input, catching cases where one model's confident answer was actually wrong.
None of these tools changed what "correct" means for the systems I test. They changed how fast I can get from "I know what needs testing" to "the test exists." That gap used to cost me hours. Now it costs me minutes, with review time added back in — which is a real trade, not a magic one.

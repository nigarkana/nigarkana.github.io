Lessons Learned from Over a Decade in Software Quality

Not a list of tools I've used. A list of things I only learned by getting them wrong first — across government systems, telecom networks, and enterprise HRM platforms.

Nigar Kana · 10 min read · Reflection · Career
Lessons Learned Exploratory Testing Automation Team Trust

Over a decade is long enough to stop learning tools by trial and error and start learning judgment the same way — by getting it wrong, noticing the pattern, and adjusting. This isn't a list of technologies. It's the handful of things that took actual project scars to learn, the kind no course teaches directly.

Automation doesn't catch the bugs you didn't think to write a test for

This sounds obvious stated plainly, and it's still the lesson I see automation-heavy teams forget in practice. A regression suite is a fixed set of assertions about a system's expected behavior — it is, by definition, blind to anything outside that set. On the Shopify e-commerce site I test today, cross-browser and cross-device exploratory sessions have surfaced functional, usability, and responsive-design issues the scripted regression suite never would have — because the scripted suite could only ever verify what someone had already anticipated. The mistake is treating a green pipeline as "no bugs" instead of "no bugs in the specific set of things we thought to check." Those are very different claims, and conflating them is how confident teams get surprised.

Exploratory testing isn't a lesser skill — it's the harder one

Early on, exploratory testing felt like the unglamorous cousin of "real" automation work. That was backwards. Writing a script to verify a known behavior is mechanical once you know what to check. Deciding what to check when nobody told you — noticing that a form probably breaks if you paste in a value ten times longer than the label suggests, or that a rejection workflow probably has an edge case around already-approved records — takes actual system understanding that no script writes itself. The best exploratory sessions I've run came from asking "what would a confused, careless, or malicious user actually do here" rather than "what does the spec say should happen."

A flaky test costs more than the time it takes to fix it

The direct cost of a flaky test is small — rerun it, maybe fix a wait condition. The real cost is what it does to trust. The first time someone reruns a failing build and it goes green, they've learned "red doesn't necessarily mean broken." The tenth time, they stop reading failures carefully at all, and a genuinely broken build gets waved through because everyone's calibrated to ignore red. I treat flaky tests as a priority defect in the automation itself, not a nuisance to tolerate — because a suite people have learned to distrust is providing negative value: it costs maintenance time and gives back false confidence.

Maintainable automation is a design decision, not a cleanup task

Every brittle test suite I've inherited had the same root cause: locators and assertions tangled together with no separation of concerns, so a single UI change meant hunting through a dozen files. Maintainability isn't something you retrofit once a suite gets big enough to hurt — it's a decision made in the first file, in the Page Object Model structure, in how test data is scoped. The cost of getting this right early is small. The cost of fixing it after eighteen months of accumulated tests is a rewrite most teams never actually get budget to do, so they just live with the pain instead.

Automation and manual testing aren't in competition

I've worked on teams that treated "more automation" as an unqualified good, chasing coverage percentage as the metric that mattered. It isn't. Automation is the right tool for verifying known behavior stays known — regression, repeatability, speed. It's the wrong tool for judgment calls: does this feel right, is this confusing, would a real user get stuck here. The projects with the best quality outcomes I've worked on used automation to free up time for exploratory and usability work, not to eliminate it. The goal was never "automate everything." It was "automate the repeatable parts so there's time left for the parts that need a person."

The most common regression suite mistake: testing the UI what the API already proved

I've seen — and early in my career, written — regression suites where the same business rule gets verified three separate times: once at the API layer, once by clicking through the UI, once again in a slightly different UI flow that happens to touch the same logic. That's not extra confidence, it's tripled maintenance cost for the same signal. The fix is scoping each layer to what only that layer can prove — UI automation for user journeys and integration, API tests for logic and validation — instead of treating "more assertions everywhere" as inherently safer.

Earning a developer's trust takes specificity, not defect counts

A bug report that says "checkout is broken" gets deprioritized. A bug report that says "checkout fails when the cart contains a product with a quantity discount and the user applies a coupon code — here's the exact repro, the expected total, and the actual total" gets fixed the same day. The fastest way I've found to earn a developer's trust isn't finding more bugs, it's finding fewer, better-documented ones — reports precise enough that they don't have to spend twenty minutes reproducing what I already reproduced. Trust compounds: once a developer learns your reports are always accurate and complete, they stop second-guessing them, and that changes how fast things get fixed.

Measure quality, not bug counts

A high defect count can mean a bad build, or it can mean careful, thorough testing on a system with real complexity. A low defect count can mean a clean release, or it can mean testing that never went deep enough to find anything. Raw counts don't distinguish between those. What I've learned to actually track and report on: escaped-defect rate (what got past testing into production, the real measure of whether the process worked), time-to-detect on the defects that do get through, and whether the same class of bug keeps recurring across releases — which signals a systemic gap, not bad luck. None of those numbers are as easy to put in a slide as "we found 47 bugs this sprint," but they're the ones that actually tell you whether quality is improving or just busywork is increasing.

None of these lessons came from a course or a certification, mine included. They came from shipping things, watching what broke, and being wrong enough times to notice the pattern. That's probably true of most of what actually matters in this job — the tools change every few years, but the judgment about what to test, how deeply, and who to trust with the answer, that part just accumulates.
